IMPORTANTE

En todos los casos, los endpoints deberán devolver el estado de la petición realizada:
    ● 200 OK: Indica que la solicitud se procesó correctamente y se devolvió una respuesta exitosa.
    ● 400 Bad Request: Se utiliza cuando la solicitud enviada por el cliente es incorrecta
        o no se puede procesar debido a parámetros faltantes, valores inválidos o problemas de formato.
    ● 401 Unauthorized: Indica que un usuario no puede realizar la acción en cuestión porque no está autorizado.
    ● 404 Not Found: Indica que el recurso solicitado no se pudo encontrar en el servidor.
    ● 409 Conflict: Indica que el registro no pudo ser eliminado o que la operación no se pudo realizar.

En los casos en que se produce un error, los mismos deben ser devueltos en un array indexado por el nombre del campo que dio error.
Los mensajes de error deben ser autoexplicativos, el usuario debe recibir la información necesaria para solucionarlo (si puede).

PROYECTO: Mensajería instantánea "WhatsApi"

En esta oportunidad la facultad desea implementar un sistema de mensajería instantánea.
Al entrar a la web, se puede ver una lista de usuarios que han indicado su perfil como es_publico. Un usuario al registrarse debe especificar un username único que empieza con
@; un nombre que incluye nombre y apellido; y una password. Al loguearse (username y password) podrá buscar a un conocido por su username o su nombre. Si encuentra al
usuario que busca, podrá seleccionarlo para iniciar un chat con el mismo.
Al iniciar una conversación, solo se puede mandar un solo mensaje hasta que el receptor responda o bloquee al emisor. Un usuario podrá ver los chats de los que participa o lo han
hecho participante. Si se ha creado un chat con alguien que no conoce, el receptor podrá bloquearlo. Si responde, la conversación se considera aceptada.
Al entrar en un chat, este muestra los últimos 5 mensajes; al hacer scroll sobre el marco superior del chat, se pueden ver mensajes anteriores. Entre las opciones de
personalización, el usuario puede elegir el nombre del chat, una descripción y un color. Estas características se compartirán con ambos usuarios integrantes del mismo.
También habrá un usuario administrador. A este se lo contacta por medio de un chat siempre presente al que se le pueden mandar dos opciones: "modificar password" o "dar de
baja". Al "dar de baja", se borran los mensajes del usuario que envió la solicitud y los chats donde estuvo involucrado.

1. Implementar los siguientes endpoints.
    
AUTENTICACIÓN
    
    Se mantiene el mecanismo anterior:
        ● POST /login: Recibe username/password. Genera un token aleatorio con expired a 5 minutos.
        ● POST /logout: Borra el token y el expired correspondiente de la tabla de usuario.
        NOTA del Middleware: Cada interacción autorizada (Authorization: Bearer<token>) estira la vida del token 5 minutos más.


USUARIOS

    ● POST /usuarios: Registro de nuevo usuario.
        ○ No requiere login.
        ○ Validaciones
            ■ username: (comienza con @), debe ser único. Puede contener letras (az-AZ) y números. Longitud: 5-12.
            ■ password: Debe contener al menos 1 minúscula, 1 mayúscula, 1 número, 1 carácter especial. Longitud: 8-15.
            ■ nombre: Solo letras y espacios. No puede ser vacío. Longitud: 2-50.
            ■ todos los perfiles se crean con es_publico = 0.
    ● GET /usuarios?search={s}&order={asc/desc}&limit={l}&offset={o}: Lista a todos los usuarios registrados cuyo criterio de búsqueda coincida con lo especificado en
        los parámetros de la url. {search} debe coincidir total o parcialmente con el campo username o nombre. El orden se aplica sobre el nombre de usuario.
    ● Además, debe seguir el siguiente criterio:
        ○ Si no se envía token o este es inválido:
            ■ La búsqueda se realiza solamente sobre los usuarios que hayan
            marcado su perfil como público (es_público = 1).
            ○ Si se envía un token válido:
            ■ La búsqueda se realiza sobre todos los usuarios del sistema,
            excluyendo al usuario logueado.
        ○ Datos que devuelve: id, nombre, es_publico, is_admin y la cantidad total de registros (independiente del limit). Si el usuario que realiza la búsqueda es
        admin se debe agregar también la cantidad cantidad de chats en los que participa el usuario buscado.
        ○ {s}, {asc/desc}, {l} y {o} son filtros opcionales. Si no se especifica, el criterio por defecto es orden ascendente por nombre de usuario.
    ● GET /usuarios/{user_id}: Devuelve el perfil del usuario con id = user_id.
        ○ Datos que devuelve: username, nombre y es_publico.
        ○ Requiere que user_id sea el usuario logueado o que el usuario logueado sea admin.
    ● PUT /usuarios/{user_id}: Editar un usuario existente. Requiere que user_id sea el usuario logueado. Se deben enviar solo los datos a modificar.
        ○ Se puede modificar el nombre, password y/o es_publico.
        ○ Requiere que user_id sea el usuario logueado o que el usuario logueado sea admin.
    ● DELETE /usuarios/{user_id}: (Solo admin) Elimina chats que involucren a user_id; todos los mensajes en los chats anteriores; y al usuario con id = user_id.


Chats

    ● POST /chats/{user_id}:
        ○ Cuerpo:
            ■ mensaje. Longitud: 1-255
        ○ Requiere login.
        ○ Flujo:
            ■ Si no existe un chat entre el usuario logueado y user_id
    ● Crea un chat entre el usuario logueado y el usuario nespecificado en user_id.
    ● El campo creado_por de la tabla chat debe indicar el id del usuario logueado.
    ● El campo usuario_id de la tabla chat debe indicar user_id.
    ● El campo nombre del chat debe indicar el nombre del usuario user_id por defecto.
    ● La descripción del chat se crea vacía por defecto.
    ● Da de alta el mensaje en el campo texto de la tabla mensaje.
    ● El campo enviado_por de la tabla mensaje debe indicar el id del usuario logueado.
        ■ Si existe un chat entre el usuario logueado y user_id y hay más de un mensaje en el chat:
    ● Da de alta el mensaje en el campo texto de la tabla mensaje.
    ● El campo enviado_por de la tabla mensaje debe indicar el id del usuario logueado.
        ○ Validaciones:
            ■ Si existe un chat entre el usuario logueado y user_id con solo un mensaje se prosigue, si y sólo si, emisor_id del primer mensaje es distinto al actual usuario logueado.
            ■ Si el campo esta_bloqueado de un chat es 1, no se pueden enviar
    mensajes al mismo.
    ● GET /chats: Lista los chats donde participa el usuario logueado ordenado de manera descendente por fecha del último mensaje recibido o enviado.
        ○ Requiere login
        ○ Datos que devuelve: id, nombre, descripción, esta_bloqueado, creado_por, usuario_id y nombre del otro usuario que integra el chat y el último mensaje recibido o enviado de cada chat, si existe.
    ● PUT /chats/{user_id}: Permite modificar los siguientes campos de un chat: nombre, descripción, esta_bloqueado y color.
        ○ Requiere login
        ○ Validaciones:
            ■ nombre: letras y números. Longitud: 3-15
            ■ descripción: letras y números. Longitud: 20-40
            ■ color: código hexadecimal.
            ■ esta_bloqueado: True o false (Una vez que el chat se bloqueé no podrá desbloquearse)
    ● GET /chats/{user_id}/historia/{quantity}: Devuelve {quantity} mensajes de un chat creado entre el usuario logueado y el user_id (máximo 10 mensajes).
        Por defecto, se devuelven los últimos 5 mensajes de un chat ordenado desde el más antiguo al más reciente.
        ○ Requiere login
        ○ Filtros opcionales: ?offset=x.
        ○ Validación: Si no existe un chat entre los usuarios, debe devolver el error.
        ○ Datos que devuelve: id, texto, fecha_creación, enviado_por.

Mensajes
    ● DELETE /mensajes/{message_id}: Elimina un mensaje cuyo id es {message_id}
        ○ Requiere login
        ○ Validaciones:
            1. El administrador puede eliminar cualquier message_id
            2. Si la acción es ejecutada por un usuario NO administrador, el message_id debe pertenecer a un mensaje enviado por el usuario logueado.
            3. Si el mensaje no existe, debe devolver el error.
        ○ Resultado: El mensaje indicado debe eliminarse de la tabla.
